# 서버 명령 시계와 본 포즈 불일치 — 역할 분리 미검증

## 1. 작업 목표
이미 수집한 서버 follower LOD1 시험에서 콜백/명령 누적 시계의 일치가 실제 본 포즈 동기화까지 뜻하는지 확인한다. 주기적 LOD 유지 정책을 구현하기 전에 실제 적용 범위와 물리/복제 위험을 기존64개체 기록·자산으로 검토한다.

## 2. 실제 수행
ANIM-server-follower-lod-network2의10,010행을 재분석했다. 첫body의 part1·3을 part2와 같은 프레임/LeftHand/요청값으로 비교했다. 콜백 증가·포즈 실제 변화·요청 안정시간을 각각 구분했고, 최대차 표본을 저장했다. 재분석을 새 실행으로 세지 않는다.
기존64개체 경로 관측1개와 수신체 비용 시험의 원본 대조1/4/5 실행을 재사용했다. FOLLOW·정상 요청0/1/2·nativeRequest 일치·전투/사망 제외 및0.5/1/2초 안정 guard를 평가하고, 별도로 안정된 공격9/10 포함 가정을 분리했다. 인식 상태를 잠그는 조건과 애니메이션 요청만 안정시키는 조건도 구분했다.
표시5파트 원본 MLOD의 GeometryLOD를 읽었다. 기존 변환 파서가 비영 face-selection을 보존하지 않도록 제한하므로 이를 그대로 우회/수정하지 않고, 모든 point/face 선택 payload를 읽고 해시로 기록하는 별도 읽기 전용 감사만 수행했다. 모델을 쓰거나 다시 변환하지 않았다.

## 3. 측정 결과
요청이 같은 fresh 콜백 표본에서 지정 전9~10초 최대 본 위치차0m, LOD1 일시 적용10~11초 최대0.409560738m였다. 같은 요청이0.2초 이상 유지됐고 실제 포즈도 갱신된14표본에서도 같은 최대값이 남았다. 최대차 시각10.5695초에서 part1/3과 대조part2의 script NativeSeconds 차이는0이었다. 이후12~13초 같은 비교는 다시0m였다. 이 값은 서버 MS 좌표의 본 포즈 차이이며 클라이언트 화면 품질 수치가 아니다.
원본64 비용 문맥에서1초 guard·정상 이동/idle만 허용한 샘플 적용률은 대조1/4/5 순서6.6101%/7.4325%/7.0738%, 공격9/10까지 포함한 별도 가정은7.8422%/8.6291%/8.3146%였다. 문맥은 기존 보수적 capture-context이며 정확한 CPU 동시 구간이 아니다. 별도70초 경로 관측 전체에서는20.5236%/21.5799%였다. 시간 비중을 CPU 절감률로 환산하지 않는다.
표시5파트 source GeometryLOD는 각각26점·36면, 선택명 component01만 존재하고230개 retained-name 합집합에 속하는 골격 본의 point 선택은0개였다. 각 source 모델 및 GeometryLOD 해시는 과거 manifest와 일치했다. 이것은 compiled ODOL/실제 native collider의 완전한 독립성 검증이 아니다.
새 게임·8/64 회귀·CPU·Present p50/p95/p99·클라이언트 포즈·영상 측정은 없다.

## 4. 원인 분석
확인: script NativeSeconds/요청 일치와 낮은 콜백 수만으로 native pose 동등성을 보장할 수 없다. 포즈가 갱신된 표본에서도 차이가 남아 단순히 갱신 사이의 같은 표본을 재관찰한 경우만으로 설명할 수 없다.
미확정: native graph 시계 손실, 블렌딩 진행, 평가/캐시 순서 중 실제 내부 원인. 가장 가까운 과거 포즈를 찾는 시간차 역추정은 블렌딩과 비단조 궤적으로 모호하므로 측정된 시간 지연으로 보고하지 않는다. 이 자료는0.5배 native 시계를 직접 입증하지 않는다.
서버 비대표 포즈의 스크립트 소비자가 적고 source GeometryLOD에 bone 선택이 없다는 점은 역할 분리 후보를 지지하는 단서다. 그러나 compiled 물리·복제·클라이언트 graph 의존성 부재를 입증하지 않는다. 서버 포즈 차이가 곧 클라이언트 품질 실패라는 결론도 내리지 않는다.
정정: 초기 적용률 분석은 INVESTIGATE 상태를 빠뜨리고 인식 상태까지 안정 key에 넣어 과소계산했다. 앞서 약1%라고 말한 수치를 정정한다. v1은 case index로 후보3도 포함했으며 v2에서 condition=control을 명시했고, v3에서 source DGBSensePolicy의 네 상태를 반영하고 두 안정성 정의를 분리했다. 초기 파일은 보존하며 최종 판단에는 v3만 사용한다. 이는 실험 gate를 낮춘 것이 아니라 읽기 전용 추정 정의/코호트 선택의 수정이다.

## 5. 검증 수준
기존 자료의 서버 본 포즈 차이 및 source GeometryLOD/해시 감사:진단 성공. 적용률은 snapshot 추정·live guard/절감 상한 아님. 주기적 LOD 유지 미구현, 실제 기능·클라이언트 시각·전체CPU 반복 성능·최종 수용 미완료. 기존 단발 LOD 후보의 비지속·미수용 판정과 발 광선 수치 기각은 유지한다.

## 6. 변경 사항
읽기 전용 분석 스크립트·파생 JSON·본 보고서만 추가했다. 원시 TSV/과거보고서·게임 소스·PBO·모델·서버/클라이언트 설정은 불변이다. 새 PBO/서명 대상이 없다. v1/v2/v3 및 실패한 기존 모델 파서의 한계를 구분했다. 자산은 재저장하지 않았다.

## 7. 원시 증거

## 8. 잔여 문제와 다음 단일 산출물
주기적 서버 follower LOD 정책은 바로 넣지 않는다. 다음 단일 산출물은 기존 네트워크/포즈 하네스를 재사용한 서버-클라이언트 역할별 포즈 비교 명세다. 필요 조건은 고정 Run·AI/이동OFF·같은5파트·대표와피해수신체LOD0 유지·지정 전/유지/복원 구간의 클라이언트 공통 본 포즈/진행률 및 역할 식별이다. native 메모리 수정 없이 지원 API만 사용한다. 클라이언트 pose 동등성/시간 진행을 확인하기 전에는 콜백 수 감소를 비용 최적화로 채택하지 않는다.
이 명세는 새 계측 도구를 반복 제작하라는 뜻이 아니다. 기존 관측기의 실제 제공 필드와 부족한 항목을 먼저 확인해 필요한 최소 변경만 정해야 한다. 클라이언트 CPU 포즈를 얻어도 실제 화면의 품질과 전체64 비용은 별도 검증이다. 기존 physics·밀침·낙하·착지·재등반 코드는 보존하고 기능 복구 개발로 확대하지 않는다.
