# 동일 방향 setter 후보64 비용 파일럿 미수용

## 1. 작업 목표

피해 수신체의 동일 방향 재설정 생략 후보가 64개체의 실제 CPU/Present 비용을 줄이는지 파일럿으로 확인한다. 원래 밀침·낙하·착지·FOLLOW·재등반·전투/피해 수신체는 유지한다. API 호출 감소를 전체 성능 개선으로 대체하지 않는다.

## 2. 실제 수행

기존 64개체 수동 미션을 격리 복사하고 플레이어를 기존 fixture.Spec.LowPoint에 고정했다. 기존 NFNetworkBodyView 카메라를 flag로 활성화했다. 두 조건 모두 CombatEnabled=true,64논리·320표시파트·64피해수신체(384네이티브 개체),같은 기존 서명 PBO/미션/해상도1280×800/VSync0/FPS상한500이다. 원본 미션은 수정하지 않았다.

같은 미션의 profile flag만 ON/OFF로 달리했다. OFF는 원래 SetOrientation을 호출하며 추가 GetOrientation은0회다. ON은 필요한 GetOrientation1회와 정확 vector 동일 비교 뒤 조건부 setter만 사용한다. 앞선8개체 진단의 post-check getter는 비용시험에서 제거했다. 공통 counter·receiver 생존 로그는 두 조건에 동일하게 추가했다. Commit에서 해당 블록을 역치환하면 원본 Commit의 위치/죽은receiver/표시파트 처리가 같음을 정규화 대조했다.

순서는 ON→OFF,각각 새 서버/일반 Steam 클라이언트/프로필·15초 ETW. 준비30초·전경·실제320표시파트 준비계수·64개체20m내·고정 카메라를 확인하고 요청했다. 수집 후 보수적 문맥을 확보해 stop flag로 정상 퇴역 절차를 요청했다. 매번 script 완료·프로세스 소멸을 확인했다.

최초 ON은 준비 로그의 일시적 'Missing logical rows'를 terminal 오류로 처리한 탓에 요청이 중단됐고,클라이언트 age90 기한을 넘었다. CSV/요청이 없어 비용 비교에서 제외했다. 원시 자료를 보존했고 기한을 완화하지 않았다. 대기 스크립트에서 같은 조건을 다시 검사하도록 해당 transient만 추가한 새 ID/경로로 재시도했다. 처음 관리자 대기 도우미는 ETW/요청 없음과 PID/생성시각을 확인한 뒤 관리자 권한으로 해당 도우미만 종료했다. 게임 서버는 강제 종료하지 않았다. 이 제외 실행을 반복 측정으로 세지 않는다.

## 4. 원인 분석

확인: 필요한 getter 비용을 포함한 현재64 파일럿은 p95 개선을 보이지 않았다. 정확동일 setter 생략 기회가8보다 적었다. 미리 고정한 Present/CPU Busy p95 모두5% 이상 개선 조건을 충족하지 못했다. 추정: 적은 생략 기회와 추가 getter/분기 비용,엔진 setter 내부의 기존 단축 처리 가능성이 후보의 실효성을 제한할 수 있다. 이들 항목을 각각 self-time으로 분리 측정하지 않았다.

반증/경계: caller setter 호출 감소만으로 전체 프레임 개선을 주장할 수 없었다. 단일쌍의 +1.6~1.7%를 후보가 실제 회귀를 일으켰다는 증명으로 해석하지 않는다. p50/p99의 이득도 한쌍에서 관측된 값이며 재현 개선으로 채택하지 않는다. 다른 경합/phase 분포와 동일PC의 서버/클라이언트 부하 변동이 남아 있다.

## 8. 잔여 문제

본 후보는 default OFF·미통합으로 보존하고 더 큰 반복 시험은 하지 않는다. 다음 단일 작업은 현재 모든 표시파트에 반복되는 transform 커밋의 native getter/setter 호출을 같은 결과의 단일 transform 처리로 묶을 수 있는지 기존 연구/공식 로컬 API 선언과 대조한 판단표다. 이미 기각된 root getter·parent attachment·4파트·단순Drive/Displace병합과 중복 여부를 먼저 확인한다. 아직 구현/성능 이득을 약속하지 않는다. 네트워크 전달·scale·physics 부수효과까지 보존 근거가 없으면 게임에 적용하지 않는다. 정상 물리 검사를 삭제하거나 미수용 후보를 누적 적용하지 않는다.
