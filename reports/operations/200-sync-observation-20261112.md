# 200개체 수동 관찰 — 서버 갱신 지연 확인
작성일: 2026-11-12 KST

## 1. 작업 목표
사용자의200개체 실제 플레이 관찰을 준비하고, 화면 프레임과 서버 상태 갱신 문제를 구분한다. 200개체 안정성 수용이나20ms목표 달성 시험이 아니다.

## 2. 실제 수행
기존 단일224 모델·13 PBO 해시와 전투/훈련체력/등반/낙하 설정을 재사용했다. 별도 미션의 개체수·인덱스 배열을200으로 확장하고 기존 종료 재진입을 막는 일회성 ExitRequested guard와 TickCount 라벨을 보완했다. PBO/키/원래 미션은 변경하지 않았다.
첫 준비는 필수 native-traversal-manifest.json 누락으로 Spawn이 실패했다. 실패를 보존하고14클립 매니페스트가 포함된 launch2로 다시 실행했다.
실제 게임 화면·200렌더/200수신체 준비 로그·상태ID0..199를 확인했다. 기존4열50행 배치로 후열은 약120m에 걸쳐 있고 일부 IDLE이므로 전원 동일 추적/교전 부하로 간주하지 않는다.
서버 전체CPU와 미션 프레임/상태 기록을 수집했다. 클라이언트의8/64개체용 고정 관측 플래그는 이번200개체 프로필에서 비활성으로 보존해 잘못된 인구 판정을 피했다.

## 3. 측정 결과
사용자 관찰: 게임플레이 화면 프레임은 괜찮지만 동기화 문제가 나타남. 화면 Present 분위수는 미측정이다.
기록된 미션1669프레임/182.45게임초:
- timeslice p50 81ms, p95 300ms, p99 300ms, 최대300ms.
- 100ms이상656개,250ms이상181개.
서버 프로세스CPU 유효248구간:
- CPU시간/벽시계초 p50 997.76ms, p95 1030.31ms, p99 1042.56ms.
이는 전체 스레드 합산 CPU이며 전체CPU사용률100%나 특정 스레드 self-time을 뜻하지 않는다.
미션 timeslice는 실제 Present/RTT가 아니며300ms에서 엔진 클램핑 가능성이 있다. updateTicks/commitTicks는 성능카운터 tick이며 ms로 계산하지 않았다.
처음600초 수집을 요청했지만 서버 종료로 부분 파일을 보존했다. 대기/종료 구간도 포함돼 전원생존 matched 성능 비교가 아니다. 8→64→200 회귀 성공이나 클라이언트/서버 성능 목표 달성 없음.

## 4. 원인 분석
확인: 서버 미션 갱신에 긴 timeslice가 기록됐고, 상당 구간에서 프로세스가 대략 논리코어 하나에 해당하는 CPU시간을 소비했다. 사용자의 화면/동기화 분리 관찰과 함께 서버 진행 지연을 유력하게 뒷받침한다.
미확인: 순수 물리/애니메이션/AI/네트워크 직렬화별 기여, 병목 스레드, 클램핑 전 실제 간격, packet loss/RTT/bandwidth 및 client측 보간 지연.
따라서 서버 지연과 통신 원인을 구분하되 네트워크가 정상이라고 확정하지 않는다. 단순 동기화 빈도 증가나 보간 추가로 CPU 병목이 해결된다고 주장하지 않는다.

## 5. 검증 수준
200개체 생성·실제 플레이 화면 진단 성공, 서버지연 부분 관측. 전체 기능·시각 품질·반복 성능·최종 수용 미완료. 사용자 화면 평가는 계측된 클라이언트 프레임 결과와 구분한다.

## 6. 변경 사항 및 종료
별도 관찰 미션/프로필/준비 기록만 생성. 배포PBO·개인키·Unity 작업 무변경, 재서명 대상 없음.
확인 시점에는 클라이언트·서버가 이미 종료돼 있었다. 로그는 manual close/퇴역/RequestExit0를 기록했으나 retained server 실제 exit는-1/forcedfalse다. 정상exit0로 보고하지 않는다. CPU sampler는 대상 종료를 감지해 부분 결과를 보존하며 종료했다. 재실행하지 않았다.
