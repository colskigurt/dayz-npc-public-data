# SupportFast64 비용 비교: 중간 판정·최적화 미수용

## 1. 작업 목표
원본 수신기를 포함한64개체384호스트에서 기존 SupportFast의 실제 CPU 절감 여부를 확인한다. 광선 생략량과 전체 물리 질의 비용을 구분한다.

## 2. 실제 수행
6실행3쌍을 사전 구성했으며4실행의15초 CPU/Present 수집을 완료했다.1/2/3번은 기존 전체 구간 검증 통과,4번은 사전 보수 활성 확인 구간에서 비활성이 발견돼 제외했다.5/6번은 실행하지 않았다. 별도 게임이 전면에 있는 것을 관찰해 새 게임 실행을 보류하고 저장 자료 분석으로 전환했다. 다른 게임의 이전 수집 구간 중첩 여부는 확인되지 않았다. 게임 코드/PBO는 변경하지 않았고, 양쪽 모두 생성 후 공격만OFF, 수신기64개와 모든 접촉·관절 검사를 유지했다. 첫 준비 실패는 시험 init.c UTF8 BOM이었으며 실패 자료를 보존하고 BOM만 제거한 별도 경로에서 실행했다.

## 3. 측정 결과
완전 비교1쌍만 확보했다. 첫 대조→후보 Present p95:18.01887→19.30152ms(+7.118%). 서버CPU/게임초:886.8131→932.8483ms(+5.191%), CPU/벽시계초+5.056%. 광선/게임초는58.231% 감소, 지지 광선 생략269,632회. 네이티브 callback 시간/벽시계 진행률의 쌍간 차이+0.056%. 발판 위 표본 비율은59.14→78.04%로 다르다. 두번째 후보 Present p95:21.79132ms, 서버CPU/게임초998.847ms이며 비교 대조4번이 제외돼 독립쌍으로 판정하지 않는다.4번 비활성59행의 age48.4847~51.4766은 요청 age31.495의 사전 보수 범위 안에 있다. 실제15초 Present 수집과의 정확한 중첩은 판정하지 않았고 사전 기준을 완화하지 않았다. p50/p99와 원시 시계·작업량은 보존 JSON에 있다.

## 4. 원인 분석
확인:광선 수는 감소했지만 첫 쌍의 전체 CPU·Present는 개선되지 않았다. 소스 StructureSupportBound는 광선4회 대신 반경0.5m SphereCast1회 및 경계/법선 검사를 추가한다. 이 추가 지지 SphereCast는 jointSweeps 카운터에 포함되지 않으므로 해당 카운터가 모든 sweep을 나타내지 않는다. useBound 성립에는 이 sweep이 필요하지만 실패한 추가 sweep도 있으므로 used는 전체 추가 sweep 수가 아니다. 추정:추가 검사의 상대 비용, 접촉/밀집 이력, 동시 외부 부하가 전체 비용을 좌우할 수 있다. 미확인:각 요인의 독립 기여와 함수 self-time. 광선58% 감소를 총 물리 비용58% 감소로 해석하지 않는다.

## 5. 검증 수준
진단 일부 성공, 비용 검증 불완전, 최적화 미수용. 최초 쌍은 서버CPU감소/Present비악화 기준을 통과하지 못했다.3쌍 반복 완료·최종 수용 아님. 모든 서버의 실제 종료-1로 정상 종료 수용도 아님.8개체 기능 통과는 이전 별도 근거로 유지하며64고저차·시각 품질·20ms 전체 목표를 이번 비용 구간으로 대체하지 않는다.

## 8. 잔여 문제
전용 측정 시간이 확보되기 전 추가 클라이언트 실행을 하지 않는다. 제외된 대조군과 남은 계획은 보존하며 교체 시험이 필요하면 새 실행ID와 제외 사유를 명시한다. 첫 쌍 실패를 유리한 후속 실행으로 지우지 않는다. 이미 줄인 광선 수와 추가 지지 SphereCast 비용을 함께 다루고, 기능 복구 개발로 전환하지 않는다. 후보는 기본OFF 유지. 원래 목표인 실제CPU감소와 애니메이션 품질·64개체 기능 최종 수용은 미완료다.
