## 1. 작업 목표

같은 16바이트 입력에서 서버가 부모 필드를 쓰는 위치와 클라이언트가 읽는 위치를 비교한다. 부모 ID 자체의 오류와 그 앞선 필드 해석의 어긋남을 구분해 수정 범위를 좁힌다.

## 2. 실제 수행

기존 1개체·8파트 격리 하네스를 재사용했다. 서버의 실제 emitter와 큐 관측에 header 진입 및 부모 필드 쓰기 직전 c0f5e9를 추가했다. 같은 emitter receiver인지 확인하고 cursor, 실제 update/presence 플래그, header mode와 dirty 상태를 읽었다. 클라이언트는 초기 입력 전에 관측기를 연결해 부모 읽기 위치와 유효 레코드 전체를 수집했다.

원본 명령 바이트 가드를 적용했고 게임 필드에는 쓰지 않았다. 같은 실행의 전체 레코드 바이트를 대조한 뒤 선언 위치의 실제 비트도 독립 확인했다. 관측 종료와 REA close, 소유 게임 프로세스 종료를 확인한 후 저장했다. 실행 중인 별도 Ghidra 분석은 중단하지 않았다.

## 3. 측정 결과

|16바이트 레코드의 부모 필드|서버 쓰기|클라이언트 읽기|

|시작 위치, 0 기준 bit offset|126|47|

같은 유효 16바이트 내용은 8/8 일치했다. 서버는 실제 부모가 없고 dirty/update도 없는 상태에서 bit126에 update0을 썼다. 클라이언트는 bit47의11을 update1/presence1로 해석했다. 위치 차이는 79비트다. 따라서 서버가 이 필드에 비정상 부모 ID를 의도적으로 써 보냈다는 설명은 이번 표본과 맞지 않는다.

서버의 뒤이은 3바이트 zero 레코드 8건에서는 부모 쓰기 위치가 bit19였다. 서로 다른 레코드 길이에 무조건 같은 위치를 적용할 수 없다는 점도 확인했다. 동일한 16바이트 내용 때문에 개별 network ID/time의 일대일 대응까지 증명한 것은 아니다.

기존 128비트 선언 범위 대비146비트 종료·18비트 초과는 별도 앞선 관측으로 유지한다. 이번에는 그에 앞서 부모 필드에 도달하기 전부터 위치가 다르다는 것을 확인했다. 새 8/64 기능 회귀, 시각 품질, Present/CPU/GPU p50/p95/p99, 할당/GC 측정은 없다. 20ms p95는 목표다.

## 4. 원인 분석

확인된 사실: 서버의 실제 부모 필드 값은 정상적인 갱신 없음이고, 클라이언트는 같은 내용의 다른 비트를 부모 필드로 읽는다. 오류 경계를 부모 setter나 부모 ID 강제 처리보다 앞선 header 소비로 좁혔다.

아직 모르는 점: 어느 앞선 필드에서 처음 어긋나는지, 생성 조건·상태 기반 생략·수신 분기 중 무엇이 원인인지, 공식 mod API로 수정 가능한 계약이 무엇인지는 확정하지 못했다. 79비트는 관찰된 두 위치의 차이이며 모든 입력에 적용할 보정량이 아니다.

기각/보류: cursor에79를 더하거나 부모 ID0을 강제하는 수정은 하지 않는다. 3바이트 레코드의 위치가 다르므로 이런 고정 보정은 다른 정상 입력을 깨뜨릴 위험이 있다. 별도 정적 분석에서 공유 dispatcher/header/guard를 대조 중이며, 함수가 아직 반환되지 않은 상태를 분석 완료로 보고하지 않는다.

## 5. 검증 수준

부모 필드의 송수신 위치와 플래그 불일치: 단일 실행 제한 진단 성공. 최초 불일치 필드·원인 확정·국소 수정·8/64 회귀·시각 품질·성능 반복 검증·최종 수용은 미완료다. 동일 자료의 비트 재해석은 새 독립 실행이 아니다.

## 6. 변경 사항

격리 미션·관측 스크립트·분석 JSON·보고서만 추가했다. 원본 바이너리, 게임 코드, 기존9PBO, 자산, Steam, 운영 서버는 바꾸지 않았다. 포트 치환 후 64자리 해시 상수 불변을 검사했고 기존9PBO의 해시·서명 검증을 실행 전에 통과했다. 신규 PBO가 없어 새 서명 대상은 없다. 진단은 functional=false 퇴역으로 종료했으며 정상 게임 종료를 주장하지 않는다.
