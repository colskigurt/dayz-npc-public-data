# 전투연결64 혼합 장면 기준선 — 단일 Present p95 18.48ms

## 1. 작업 목표

전투 연결을 유지한 현행 64개체 혼합 장면에서 실제 프레임 비용을 확인한다. 전투 OFF·320호스트 평지 시험과 구분하며, 새 최적화 효과를 주장하려는 비교가 아니다.

## 2. 실제 수행

기존 5파트 NPC·전투/피해 수신기·훈련 체력 복원·컨테이너 씬·고정 카메라를 사용했다. 플레이어 목표를 지면10초→낮은 발판10초→높은 발판10초로 반복했다. 현재 엔진과 서명된 기존11PBO를 해시에 고정했다. 30초 Present와 거의 같은 구간의 서버 프로세스 CPU31표본을 수집했다. 준비 오류가 있던 첫 실행은 보존하고, 수정된 새 실행만 이번 기준선으로 사용했다.

## 4. 원인 분석

이 고정 혼합 장면의 단일 Present p95는20ms 아래였다. 따라서 현재 모든64개체 장면이 과거65~70ms라고 표현할 수 없다. 반대로 이전 수동 플레이27.66ms와 엔진·입력·카메라·수집 검증 조건이 같지 않아 개선율을 계산할 수도 없다. CPU Busy와GPU Busy 패턴은 CPU측 검토의 맥락이지만 특정 물리/본 함수의 순수 비용을 입증하지 않는다. 서버 틱 p95=43ms와 실제 애니메이션/이동 부드러움도 별도로 판정한다.

서버 게임시계는 기존 저부하 수집기 설계상 CPU 표본의 처음/마지막에만 읽는다. 중간29행의 빈 시계 열은 수집 실패가 아니다. 이 자료로 구간별 프로세스 CPU나 클라이언트 Present를 임의 분배하지 않았다. 별도 stage-context-v2에 이 경계를 명시했다.

## 5. 검증 수준

준비·수집·전체 구간 인구/호스트/전경 검증: 단일 기준선 진단 성공. 이 장면의 단일 p95≤20ms: 관측됨. 반복 성능 수용·새 최적화 개선·전역20ms·전체 경로/피격/사망/시체·시각 품질 최종 수용은 미완료다. 서버는 RequestExit0 후 실제exit−1이며 정상0종료 통과가 아니다. 클라이언트 정상 닫기와 수집기 종료를 확인했다.

## 6. 변경 사항

격리 시험 미션·고정 자극·관측/수집 설정만 사용했다. 실제 플레이의 전투/시체 포함Commit을 그대로 재사용했다. 기존 NPC 알고리즘·PBO·애니메이션 자산/시계·서명은 변경하지 않았다. 새 서명 대상 없음. 실패한 최적화 후보를 켜지 않았다.

## 7. 원시 증거

실행 ANIM-mixed-gameplay64-baseline-retry2. Present CSV, closed/consumed, 서버CPU CSV/JSON, gameplay/mixed-hosts/part-command-clock/server-frame/visual-app TSV, 고정계획·미션·전퇴역 기록을 연결했다. 공개 JSON에는 집계·파일명/SHA256만 제공하고 절대 경로/PID/개인정보는 제외했다. 이전 준비 실패는 독립 성공 반복으로 세지 않는다.

## 8. 잔여 문제

이 표본만으로 추가 미세 최적화를 계속하지 않는다. 사전에 정한 방향대로 기준선의 반복성 확인과 전체 경로·실제 화면 검증을 우선한다. 현재 서버 틱 간격과 실제 근접/장시간 밀집 장면의 범위는 남아 있다. 반복 표본이20ms를 넘거나 다른 실제 장면에서 재현되면 해당 장면의 동기화된 비용 근거로 고비용 실행 소유자를 좁힌다. 이미 실패한 backoff·solid·broadphase 후보의 기준을 사후 통과로 바꾸지 않는다.
