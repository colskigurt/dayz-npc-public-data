# 현행 단일 파트64 CPU 부분 귀속 — 물리 질의와 VM 비용을 분리해 다음 후보 선정

## 1. 작업 목표
현재 단일 렌더+피해 수신체 구성의 실제 서버 CPU 경로를 확인한다. 과거8파트·5파트의 비용 비율을 현재 값으로 쓰지 않고, 실패한 미세 캐시·호스트 교체를 반복하기 전에 후보 선택에 필요한 공백을 채운다. 기존 NPC 기능과 애니메이션은 변경하지 않는다.

## 2. 실제 수행

첫 구형 Windows PowerShell 도우미는 준비 기록 없이 종료됐다. 현재 구형 셸의 실행 정책Restricted를 확인했지만 최초 stderr가 없어 직접 원인으로 확정하지 않는다. 같은 승인 범위의 현재 런타임 PowerShell에서는 관리자 토큰 준비 기록과 실제 PID를 확인했다. 실행 정책·권한 그룹·서비스는 변경하지 않았고 게임은 일반 Steam 경로로 실행했다. 관리자 도우미는 자기 WPR instance만 시작/종료했다. 대기 시도와 실제 CPU 수집1회를 구분한다.

## 4. 원인 분석
확인: 현행 단일 파트에서도 선정 물리 질의 경로가 CPU 표본에 나타나며, 그 두 경계만으로 설명되지 않는 VM 실행 표본도 많다. 실제 작은 Ray 중복22건만 줄이는 후보를 주력으로 삼을 근거가 부족하다. 반대로 물리 질의가 병목에서 사라졌다고 할 수도 없다.
중복 검토: receiver 방향 setter 생략64 파일럿은 p95 개선 gate 미달이었다. 동일 상태 판정의 eager 배열 재사용도 기존 밀집−20.57%/희박+5.60% 국소 결과로 일반 적용 미수용이었다. 이를 새 성공 후보로 재포장하지 않는다.
새로 검토할 차이는 pair에서 처음 필요할 때만 상태를 계산하는 lazy 방식이다. 희박에서 비용을 만든 매 Update 전처리를 제거할 수 있는지 묻는다. 이웃/위치/힘/물리 결과는 공유하지 않으며 갱신 주기·등반 시도·애니메이션은 그대로다. 현재13 PBO의 Crowd 소유자 목록과 base source 패킹 일치를 확인했고 AccumulatePair/Update의 별도 교체는 해당 목록에 없었다. 정확한 무효화·재진입·호출 문맥 증명이 아직 필요하다. 예상 전체 개선률은 제시하지 않는다.

## 8. 잔여 문제와 다음 단일 산출물
다음은 지연 계산 상태 재사용의 소스 계약과 기존 합성 하네스 선별이다. 기존 eager 캐시와 다른 점은 pair0에서 prepass0, 개체 수 변화 외 per-frame N개 초기화0, 최초 소비 시점 계산·갱신 세대 안에서만 재사용이라는 의무다. DEAD/높이 필터·쌍 순서·힘 누적·최종 플레이어 처리·실제 물리 질의는 유지한다. 상태 변경/재진입을 막거나 무효화하지 못하면 runtime으로 확대하지 않는다.
기존512행과 밀집/희박 하네스를 재사용하고 중간 밀집도도 포함한다. 기준은 첫 측정 전에 동결하고 국소 이득이 없으면8/64를 만들지 않는다. 통과해도 전체 CPU 이득은 별도 비교해야 한다. 현재 목표를 작은 메서드의 좋은 퍼센트로 대체하지 않는다.
이번 데이터만으로 특정 소스 함수의 순수 비용·현재 모든Native animation 비용·할당/GC를 알 수 없다. 스택 누락을 채우기 위한 맹목적 재수집이나 원인 미확정 종료 크래시 복구로 범위를 확대하지 않는다. 전체 기능·화면·성능 목표는 계속 미완료다.
