# 다음 단일 후보: 군집 갱신 안에서 필요할 때만 이동 가능 상태 재사용

상태: 구현 전 소스 검토. 아직 구현·컴파일·비용 시험·채택하지 않았다.

## 기존 연구와 차이

`work-reduction-review1/crowd-eligibility-factor1`은 같은 상태 재사용 계열이다. 512 합성 입력에서 결과가 같았고 밀집 국소 중앙 약20.57% 이득이 있었지만, 희박에서는 약5.60% 악화해 일반 적용 gate를 통과하지 못했다. 이 기록을 새 아이디어로 포장하거나 그대로 재시험하지 않는다.

검토할 차이는 **모든 개체를 매번 미리 판정·저장하는 전처리를 없애는 것**이다. 실제 쌍이 DEAD/높이 필터를 통과해 처음 상태가 필요할 때만 그 개체의 `Movable && !EntryPressurePriority`를 계산하고 같은 `Crowd.Update` 안에서 재사용한다. 개체 쌍이0이면 상태 판정이나 배열 재초기화 전처리를 하지 않는 것이 핵심 의무다. 거리·위치·속도·힘·물리 질의 결과는 캐시하지 않는다.

## 수정 가능한 범위와 안전 계약

- 현재13개 PBO의 Crowd 정의를 확인했고 base source가 패킹 원문과 같다. 추가 계층은 ConsumeContact/Displace를 확장하며 AccumulatePair/Update의 다른 구현은 이 제한된 소유자 검색에서 확인되지 않았다.
- AccumulatePair는 현재 base Update에서만 호출된다. 후보가 활성화된 해당 호출 구간에서만 재사용한다. 다른 호출 문맥과 OpenTraversal=false는 원래 경로로 돌린다.
- DEAD/높이 조기 반환, 격자 열거 순서, PairCandidates/ContactPairs, 힘 계산·누적 순서, 최종 플레이어 처리는 그대로 둔다. 그 부분의 Movable은 캐시로 바꾸지 않는다.
- 캐시는 개체 배열 인덱스와 갱신 세대에 묶고, Body 수 변경·세대 넘침·재진입·갱신 밖 접근에 안전한 무효화가 필요하다. 새 per-frame 배열 할당·N개 prefill을 넣으면 기존 희박 실패 원인을 되풀이하므로 거부한다.
- 재사용되는 입력은 Agent.State, Combat Active/Dead/PendingDeath, Traversal Phase/Active/Action, ManagedPeerContacts와 EntryPressurePriority다. 해당 쌍 루프가 이 필드를 바꾸거나 재진입 callback을 실행하는지 source proof를 먼저 마쳐야 한다. 증명되지 않으면 runtime 구현으로 넘어가지 않는다.
- 물리·발 지지·낙하·착지·등반 재시도·애니메이션 갱신율은 변경하지 않는다. 이동/접촉 제안을 합치지 않는다.

## 예상 이점과 비용

이웃 쌍이 많은 경우 반복 스크립트 상태 조회를 줄일 수 있다. 이전5파트 진단의 Movable946861회/30게임초는 호출 규모의 근거이며 현재 빈도나 순수 CPU 비용이 아니다. 현행 단일 파트 CPU 스택에서도 VM 실행 경로가 관찰되지만 이 메서드의 전체 CPU 기여는 아직 분리되지 않았다. 성능 절감률은 제시하지 않는다.

세대 검사·배열 접근·조건 분기와 상태 보관 비용이 새로 생긴다. 중간 밀집도에서는 cache miss가 많아 원래보다 느릴 수 있다. 그래서 밀집 결과만으로 통과시키면 안 된다.
